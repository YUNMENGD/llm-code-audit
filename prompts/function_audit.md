# 输出要求
只输出一个 JSON 数组，不要任何其他文字、不要 markdown 围栏。每个元素字段：
- rule_id: 命中的知识条目 ID（如 CWE-89、LOG-002）；知识库外的问题用 DISCOVERED-序号
- category: security | logic | style | engineering
- severity: critical | high | medium | low（按可造成后果定级，禁止全部 high）
- title: 一句话问题描述（≤30 字）
- line_start / line_end: 真实行号（整数）
- function_name: 所在函数名或 null
- evidence: 逐字引用问题代码行（不得改写，将用于自动回溯校验，改写即判为无效）
- analysis: 数据流/控制流层面的论证：输入从哪来、为何能到达危险点、为何现有防护不足
- impact: 触发条件 + 影响范围
- fix: 可直接粘贴的修复代码或明确步骤
- confidence: 0~1（证据确凿≥0.9；需要外部条件佐证 0.5~0.8；纯猜测 <0.5，低于 0.4 的问题不要报告）

# 判定纪律
1. 每条问题必须能指向具体行；说不出行号就不要报。
2. 区分"确实有缺陷"与"风格偏好"：后者只在明显违反主流规范时报，category=style、severity=low。
3. 同一根因的多处表象合并为一条，不要逐行刷屏。
4. 代码无问题时输出 []，不要为了凑数编造。
5. 修复建议必须保持原有功能，不能引入新问题（如为修 SQL 注入改成字符串过滤转义是错误修法）。
