# 调优发现清单（v0.1 首次真实试跑 · qwen-plus · examples/vulnerable_app.py）

> 来源：2026-09-04 端到端试跑，24 个检出（12 静态 + 12 LLM），耗时 80s。
> 本清单是 D13 Prompt 迭代、D15 验证机制、D19 调优的直接输入。逐条认领后转正式 Issue。

## T1【高】修复方案安全性把关 —— Prompt 缺"修复自查"
- 现象：#7（eval RCE）模型给出 `eval(expr, {"__builtins__": {}}, {})`，该写法可被
  `().__class__.__bases__[0].__subclasses__()` 等手段逃逸，是已知**不安全修复**。
- 处理：`function_audit.md` / `file_audit.md` 判定纪律新增一条：
  "fix 本身不得引入新漏洞；不确定是否安全的修复方案，改为文字说明而不是代码。"
- 负责人：王富春（D13）

## T2【高】缺上下文时的过度推断 —— 置信度校准
- 现象：#10 仅凭 `get_user(user_id)` 参数名就判定 IDOR（CWE-862），confidence 0.95。
  函数没有调用方信息，是否越权取决于上层是否鉴权，模型无权断言。
- 处理：Prompt 增加规则："判定依赖外部上下文（调用方/部署环境/鉴权中间件）的问题，
  confidence 上限 0.7，且 fix 写成『建议人工核查：…』"。
- 同步改 `validate.py`：detector=llm 且 confidence<0.5 直接过滤，0.5~0.7 标注"待人工确认"。
- 负责人：杨梦颢（D15）

## T3【中】同一根因拆成多条 —— 聚合策略
- 现象：第 43 行裸 except 被拆成 #19(规则) #20(异常吞噬) #21(缺日志) 三条。
  各有道理但刷屏，报告可读性差；#1/#2、#3/#4、#5/#11、#16/#17 等静态+LLM 同点成对出现。
- 处理：`validate.dedupe()` 从 (path, rule_id, line) 改为两级：
  ① rule_id 不同但 CWE 映射相同且行号重叠 → 合并为 detector=both，保留最完整描述；
  ② 同行相邻的 style/engineering 低危问题合并为一条"综合"。
- 需要建 `knowledge/rules/cwe_map.json`（R-SEC-001 ↔ CWE-89 等映射表）。
- 负责人：陈文飞（D17 前）

## T4【中】模型输出的代码格式噪声
- 现象：#4/#13/#22 的 fix 字段含字面 `\n`、缩进错乱，渲染进代码块后不可直接复制。
- 处理：`Issue.from_dict()` 对 fix/evidence 做 `\\n` 还原与缩进规范化；
  渲染前跑一次 `ast.parse` 尝试，失败则降级为纯文本展示。
- 负责人：翁思琪（D16 报告生成时一并做）

## T5【低】耗时与并发
- 现象：8 个函数单元 80s（≈10s/次调用），真实项目上千函数不可接受。
- 处理：D17 起加并发池（asyncio/线程，4~8 并发）+ 函数级结果缓存
  （源码 hash → 已审结果，增量审计时跳过未变更函数）。
- 负责人：杨梦颢
