## 一、总体目标（20 天后应达成）

1. 《系统详细设计文档》v1.0 评审通过（架构、模块划分、接口定义）。
2. 缺陷知识库初版：≥50 条带来源标注的知识点（安全漏洞 / 逻辑错误 / 规范问题三类）+ 代码规则库初版，且完成向量化、可检索。
3. 多粒度审计工作流设计稿 + Prompt 模板集（函数级、文件级、工程级各一套）。
4. 最小闭环 Demo：给定一个含已知漏洞的 Python 函数，系统能输出结构化的审计结果（问题类型、定位、风险分析、修复建议）并生成一份报告。
5. GitHub 仓库协作流程跑通（分支规范、PR 审查、每日提交）。

## 四、风险与依赖

1. **LLM API 额度**：D12 起会频繁调用模型，需提前准备可用 API key 与少量额度预算；建议同时封装两个模型备用。
2. **知识库来源合规**：所有知识点必须标注出处（CWE 编号、OWASP、权威文档），结题答辩会看可解释性。
3. **一致性实验成本**：多次运行比对（D15 方案）会放大调用量，先小规模试。
4. **人员协调**：2025 级三位成员课业波动大，每日任务保持"半天可完成"粒度，异步推进为主，每天固定时间在仓库留一条提交或 issue 评论作为进度心跳。

## 五、协作流程（GitHub）

- 仓库结构：main（受保护）← PR ← feature/模块名
- 每个 PR 至少一名非作者成员 review 后合并
- 文档类（设计稿、知识库）也走 PR，保留修改历史，方便写结题报告时回溯
- 每天收工前：本地 git pull --rebase，避免冲突堆积
